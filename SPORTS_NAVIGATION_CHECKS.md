# Sports navigation and layout refresh

## Experience

- Keep the existing seven-sport / 38-competition ESPN catalog. Country/area metadata categorizes configured competitions only; it does not add a provider, advertise unsupported leagues or infer a fixture's location from a venue/team.
- Combine sport, region, country/area, competition, status, team/league/country search and loaded date filters. Sport/region changes preserve compatible country/competition choices and clear incompatible ones; Reset filters clears filters while retaining the chosen list/card layout.
- Browse country → competition in a desktop sidebar, or an expandable mobile browser. Provider-supplied fixture counts are labeled as **loaded** counts, not today's full schedule. Cross-border leagues retain multi-country labels; international tournaments are not assigned to one nation.
- Default to a denser vertical match list with full team names and real/missing scores. Switch to the existing cards without losing filters, match links, sharing controls, venue information, or race-specific presentation.
- Quick All matches / Live / Upcoming / Results controls share state with the existing status select. Mobile keeps country/competition/search prominent and places region/status/date controls under More filters. Active advanced selections are indicated when collapsed.
- First match stays above 700px in the 320px-wide browser fixture, without hiding the public header/navigation in the actual app. The tests check visible input bounds and still verify the original first-screen limit, 44px sport buttons, full three-digit scores, dark mode and no horizontal page overflow.
- Dates use Africa/Nairobi (EAT) and filter only fixtures already supplied by the scoreboard. No historical requests, invented schedules or unreported countries are added.
- Match details include a competition breadcrumb linking to `/sports?league=<slug>`, which SSR initializes validated URL-backed filter state. Unknown/malformed filter values fall back to supported defaults; no input is used to build an upstream URL.
- Match sections retain statistics, lineups, player tables, event updates, manual refresh and honest missing-data states. Larger scores and sticky section controls make navigation clearer. Comparison bars render only for two reported non-negative scalar values with matching units and a positive total; no missing/zero-total/ratio statistics are fabricated or compared. Labels explain which team each color represents.

## Contracts preserved

No changes to ESPN endpoint identifiers, Accept-only request headers, transport cache/concurrency/retry budgets, odds filters/prices/premium flags, API authentication, Google verification, SEO canonicals, public header/tabs, or About/Privacy pages. Scores still poll every 45 seconds when visible, manual refresh uses its existing API contract, failed refreshes retain data, and detail links disable prefetch. Motorsport retains its race/driver view, never a fictitious two-team match.

### Match-detail review: original priorities

Existing details already provide score/status, EAT kickoff, venue, competition navigation, team-stat comparisons, lineups/rosters, player statistics, reported events, sharing from score cards, source diagnostics and safe return navigation. The review identified the following priorities. Items 1–3 are implemented by the follow-up below; item 4 remains deferred:

1. **Recent form (last five completed games per team)** — useful pre-match context. Fetch actual dated team results on demand; clearly state competition scope and incomplete coverage. Never infer form from the loaded scoreboard or use results after a historical match's kickoff.
2. **Head-to-head** — recent meetings with dates, competition and final scores. Validate both team IDs, disclose limited history and avoid presenting a sampled list as an all-time record. Extra-time/penalty outcomes need explicit labels.
3. **Richer match information** — reported round/stage, referee and attendance are a low-request-cost enhancement when present in the existing summary. Keep missing fields absent/explicit; do not invent officials or attendance. A venue map requires a separately reviewed mapping source.
4. **Next fixtures for each team** — useful follow-on navigation, using separately bounded schedules and EAT kickoff labels. Distinguish “after this match” from “upcoming now” for historical pages.

Injuries, suspensions, formations on a pitch diagram, live text commentary beyond reported events, and qualification/relegation color zones should wait for reliable structured coverage. Do not invent players' pitch coordinates, complete injury lists, commentary, table rules or win probabilities. Existing lineups, statistics and events do not need duplicate tabs.

## Recommended-next follow-up: form, head-to-head and match information

- Added **Form & H2H** and **Match info** sections without replacing Statistics, Lineups & rosters, Player stats, Match events or League table. Anonymous header/navigation, scoreboard return context and existing score/odds/F1 behavior remain unchanged.
- Match info reads reported round/stage, attendance and named officials/roles from the existing summary, alongside competition, season, EAT kickoff and venue. Reported attendance of zero is retained; absent fields stay `—`. Refresh validates optional metadata before rendering; old responses without these fields remain supported. There are no extra provider requests for this section.
- Form/history is fetched only on first opening its section, through public `/api/sports/matches/[league]/[eventId]/history`. The server derives team IDs, kickoff and season from the validated, shared match summary—not client-supplied teams, URLs or dates. Missing season/kickoff or unsafe IDs produce a clear unavailable state, not an invented pre-match record.
- History requests team schedules from the fixed catalog league at `/apis/site/v2/sports/{sport}/{league}/teams/{id}/schedule?season=YYYY`, for the reported match season and previous season. Each payload must confirm its team and requested season. Explicitly different competition metadata is excluded. Other competitions are not separately fetched. The UI labels the requested competition, two-season scope, coverage limitations and latest-first ordering; no all-time record or complete-history claim is made.
- Up to five usable completed results per team and five previous meetings are selected separately from the full bounded input, so head-to-head is not just the intersection of the two visible five-game form lists. Kickoffs must be strictly before the selected match; the selected event, future, unfinished, cancelled/postponed/abandoned/suspended, invalid and mismatched-team fixtures are excluded. Entries are deduplicated; conflicting records are omitted rather than silently choosing a score. The schedule parser processes up to 500 supplied events per response and does not follow pagination or Core references.
- Zeroes and complex sport scorelines (such as cricket wickets) are preserved. Form uses provider winner flags first. Numeric tied scores consider supplied shootout scores and penalty status; unknown shootout winners do not become fabricated draws. Non-numeric scores never acquire calculated W/L outcomes; an explicitly reported draw/tie can be labeled as such. Reported extra-time/penalty status is retained. Result links preserve the safe scoreboard return context and disable prefetch.
- Two independent history jobs can run per process, each requesting at most four schedules in parallel: at most eight upstream schedule requests. Those requests share an eight-second deadline, Accept-only headers and no retries. An uncached match summary can take its separate existing eight-second budget first; the browser has a twenty-second request deadline, and the route has a thirty-second execution limit. Coalescing, a 100-key cache, five-minute ready TTL and fifteen-second partial/unavailable TTL bound repeated work.
- Partial initial loads disclose unavailable seasons and show only usable results. Failed or partial refreshes retain the previously loaded history. Empty successful schedules are not presented as proof that the teams have never met. Tab switching retains history without refetching; ordinary summary refresh does not fetch history or standings. Explicit history refresh is independent, and unmount aborts the browser request.
- Verification: **135 sports unit/API tests, 16 SEO tests, 93 Chromium browser tests**, TypeScript, changed-file ESLint and production build. Browser coverage includes anonymous/mobile/dark-mode layout, safe keyboard-focusable result links, lazy/single-flight history, summary-refresh independence, malformed/future response rejection, partial/empty/unavailable states, stale-result preservation, metadata validation and request deadlines. Provider tests exercise identity/season checks, score formats, penalties, cross-competition filtering, caching/coalescing, HTTP/network/schema/timeout behavior and job limits.
- These checks use controlled fixtures. Live ESPN team-schedule availability, full season/postseason coverage, historical completeness and deployment access are **not verified** in this network-restricted environment. Deployment review is still required. Next fixtures, injuries, suspensions, all-time head-to-head, pitch coordinates and prediction models remain out of scope; no database or credential changes are needed.

## ESPN predictions: five endpoint families

- Added on-demand **Show ESPN insights** to real prediction/odds cards, and a **Predictions & odds** section on match details. Anonymous users can open both. The existing fixture/odds load, polling, sharing/polls, premium labels, all match sections, NBA/NFL pages, crests and safe return navigation are preserved. Neither initial SSR nor ordinary score/odds refresh fans out to the five new sources.
- Public no-store endpoint: `/api/sports/matches/[league]/[eventId]/insights`. It derives catalog league, home/away team IDs and a separately reported competition ID from the existing shared match summary. It never assumes event ID equals competition ID. Missing summary/team identity skips all sources; missing competition ID permits only league-level predictions and explicitly skips event-scoped routes.
- Fixed endpoint families: Core v3 `/sports/{sport}/{league}/predictions?eventId={event}&limit=50`; Core v2 `/sports/{sport}/leagues/{league}/events/{event}/competitions/{competition}/predictor`, `/probabilities?limit=100`, `/powerindex` and `/odds?limit=50`. This change does not fetch season power-index leaders, historical odds movements or individual play endpoints. All configured two-team match leagues can request the adapters; coverage is not promised. Motorsport remains a separate race view, not a fabricated two-team prediction.
- Reference: the owner-supplied catalog at `https://github.com/pseudo-r/Public-ESPN-API/blob/3796c6a7c0b0c496c1f62408b0792e23254cd930/docs/core-endpoints.md`, particularly lines 187–206 and 474–476. This generated WADL catalog explicitly warns that routes may be internal, obsolete or sport-specific and are not individually live-verified. The same revision's response schemas describe `gameProjection` percentages and Core probability fractions. Tests use controlled schema fixtures; an advertised route is not proof of live response compatibility.
- Each source is independent: ready, empty, unsupported format, unavailable or skipped. Unknown/reference-only formats are not guessed or dereferenced. No automatic host/route fallback, pagination, provider redirects, cookies or spoofed headers. All requests retain the existing Accept-only header policy. A returned HTTP 403/404 remains source metadata, distinct from a missing application route.
- Conservative adapters: game projections accept identified home/away `gameProjection` fields (or named statistics) on a 0–100 scale; league predictions additionally require one unambiguous explicit matching event. Core probabilities accept named 0–1 fields and preserve supplied tie probabilities. Explicit mismatches, out-of-range values and over-100% sums are rejected. Missing sides/draws are not synthesized, complemented or normalized. Multiple probability records are selected only by reported timestamps, not array position; absent timestamps remain unknown. Output is labeled as current reported data, never a historical pre-match snapshot or an accuracy claim.
- Power-index adapters display only named match-team metrics from supported inline team/stat blocks, without treating ratings as win probabilities. Core odds reuse the existing American/decimal conversion, retain zero spreads and use one bookmaker's row without mixing markets/providers. Core odds are displayed separately from the original scoreboard odds; neither is rebranded as a model estimate. No automatic picks, expected-value recommendations, calibration claims or stored historical forecasts are introduced.
- Parsing/rendering is bounded (100 inline items, 20 power-index teams, 20 statistics/team and 40 displayed metrics). Source pagination/count caps are disclosed. Body reads are capped at 2 MiB per source. Five Core requests share an eight-second deadline, with no retries; the existing summary may take its separate eight-second budget first. Two distinct jobs per process bound new Core concurrency to ten, coalescing identical requests. Cache: 100 keys, 60 seconds for ready data, 15 seconds for partial/unavailable. Route execution limit: 30 seconds; browser deadline: 20 seconds with unmount abort. These limits are per process, not a global provider rate guarantee.
- Explicit independent refresh retains the last successful snapshot if a previously available source fails or becomes unsupported. Closed/reopened panels and switched match tabs retain data without refetching. Nested API responses, event references and Core HTTPS source links are validated before rendering. Provider timestamps and fetch times are separately labeled; fetch time alone is not evidence of model freshness. Names/metrics are React-escaped, not rendered as HTML.
- Validation: **158 sports unit/API tests + 17 SEO tests + 110 Chromium browser tests**, TypeScript, changed-file ESLint (no errors, two existing image-optimization warnings), production build (existing Next file-tracing warning) and diff check. Tests cover five adapters, all catalog URL mappings, different event/competition IDs, scales/sums/zeroes, foreign identities, empty/unsupported/reference-only/partial data, HTTP/network/timeout/oversized payloads, coalescing/cache/concurrency limits, mobile/light/dark layout, lazy and single-flight UI, stale refresh retention, invalid responses and browser deadlines.
- Real production Next.js smoke: the public insights route returned a five-section no-store envelope and rejected an unknown catalog league; `/sports/predictions` rendered anonymously at 375px without overflow or runtime/hydration errors. The actual insights result was unavailable in this restricted sandbox. **Live Core endpoint access, schema compatibility and per-league prediction coverage remain unverified** and must be reviewed on deployment. The preview runs in offline database mode; no schema, credential or database changes were made.
