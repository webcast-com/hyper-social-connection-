# Prisma setup — status

**Prisma ORM 8 is the app's data layer.** There is no generated client and no
driver adapter any more. `prisma/schema.prisma` is compiled into a *contract*
(`src/prisma/contract.json` + `contract.d.ts`, both committed), and the client
in `src/prisma/db.ts` is built from that contract at runtime over one `pg`
connection pool.

## Layout

| File | Purpose |
| --- | --- |
| `prisma.config.ts` | Prisma 8 config: contract source, output directory, `DATABASE_URL`, and the `composer` section `prisma deploy` reads |
| `prisma/schema.prisma` | Canonical schema and the source of the contract. camelCase fields `@map` to the physical snake_case columns |
| `src/prisma/contract.json`, `contract.d.ts` | The emitted contract. Generated by `npm run db:generate`; committed; never edited by hand |
| `src/prisma/db.ts` | The Prisma 8 client (`db`) and the shared `pg` pool |
| `src/prisma/connection.ts` | Where the database comes from: the one `prisma deploy` wired to the service, otherwise `DATABASE_URL` |
| `module.ts`, `service.ts` | What `prisma deploy` and `prisma dev` deploy (see "Deploying") |
| `src/prisma/tls.ts` | TLS for a `DATABASE_URL` connection (`DATABASE_SSL`, `DATABASE_CA_CERT`), shared by the app and the `prisma db …` commands |
| `.github/workflows/database-migrate.yml` | Applies the migrations to the Supabase database when the schema changes on `main` (see [DATABASE.md](DATABASE.md), "Using Supabase") |
| `.github/workflows/prisma-deploy.yml` | Deploys to Prisma Cloud. Runs only when started by hand |
| `src/lib/prisma.ts` | What app code imports: `db`, the `hasDatabase` offline flag, `ensureDbConnection()`, and the raw SQL helpers `rawQuery` / `rawExecute` / `rawTransaction` |
| `migrations/app/` | Migrations planned from contract changes. Committed |
| `src/lib/migrate.ts` | Idempotent boot DDL: tables outside the Prisma schema (group calls, sports picks, highlights) and the triggers/functions Prisma can't express |
| `src/lib/social-ddl.ts` | Trigger/counter patches applied by migrate on every boot |
| `src/lib/seed.ts` | Boot auto-seed (runs when the database is empty) |
| `prisma/seed.ts` | CLI seed (`npm run db:seed`): creates or updates the demo users |
| `scripts/verify-prisma.ts` | One read; prints `✅ Connected` or the exact error (`npm run db:verify`) |
| `tools/prisma-next-shim/` | Makes the `prisma-next` command Prisma Compute's deploy step calls run this repo's `prisma` CLI (see "Deploying") |

## Commands

```bash
npm run db:generate          # prisma contract emit: schema.prisma → src/prisma/contract.*
npm run db:plan -- --name x  # prisma migration plan: write a migration for the contract change
npm run db:migrate           # prisma db migrate: apply committed migrations to DATABASE_URL
npm run db:check             # prisma db verify: does the database match the contract?
npm run db:seed              # create or update the demo users
npm run db:verify            # connectivity check through the app's own client
npm run db:local             # zero-Docker local Postgres (see DATABASE.md)
```

Prisma 8 needs Node 22.18 or newer.

## A new database

Create the tables with Prisma **before the app first runs against the
database**:

```bash
DATABASE_URL=postgres://… npm run db:migrate
```

Order matters. If the app boots against an empty database first, the boot DDL
in `src/lib/migrate.ts` creates the tables itself, without the unique indexes
and the marker Prisma expects. The app runs on such a database, but
`prisma db migrate`, `db sign` and `db update` all refuse it afterwards.
Migrating first and booting second is fine: the boot DDL then only adds its
own tables and triggers, and `npm run db:check` still passes.

## Changing the schema

1. Edit `prisma/schema.prisma`.
2. `npm run db:generate`
3. `npm run db:plan -- --name <slug>`
4. `npm run db:migrate`
5. Commit `src/prisma/` and `migrations/` with the code change.

## Deploying

The live site is served by Vercel with a Supabase database: see
[DATABASE.md](DATABASE.md), "Using Supabase". Prisma stays the query layer in
the code; Prisma Cloud below is an optional second place to run the app.

### Prisma Cloud (started by hand)

The app is declared for `prisma deploy` in three files:

| File | Purpose |
| --- | --- |
| `module.ts` | The app: a Postgres database, this Next.js service wired to it, and a public URL. Its `appRoot("hyper-social-connection-", …)` name is the Prisma project the app deploys into |
| `service.ts` | The Next.js service: what it depends on (the database) and what it exposes (HTTP) |
| `prisma.config.ts` → `composer` | Points the CLI at `module.ts` and sets the region a new project is created in |

`.github/workflows/prisma-deploy.yml` runs when it is started from the Actions
tab on `main`: `npm ci`, `npm run build`, then `prisma deploy` to the
`production` environment. It no longer runs on every push; it failed there,
and the site does not depend on it. `npm run prisma:deploy` does the same from
a terminal.

A deploy finds its project **by name** in the workspace and creates it when no
project has that name. The name in `module.ts` is `hyper-social-connection-`.

The workflow has two ways to authenticate:

- The repository secret `PRISMA_SERVICE_TOKEN` (a service token created in the
  Prisma Console). It can create the project, so the **first** deploy needs it.
- Without the secret, the short-lived token Prisma issues to a repository that
  is connected in the Console. It can deploy into a project that already
  exists, but creating one is refused ("The management API rejected the service
  token").

The workspace's older project, `hybrid`, cannot be the target. Its `main`
branch already holds the `Development` database, the `hyper-blog` bucket and
the `nextjs-postgresql-template` app, and a deploy refuses a branch that has
resources it did not create. The fix it suggests, deleting the environment,
would delete that database and bucket. Leave that project as it is; this app
deploys into its own project.

Each deploy applies the committed migrations in `migrations/app` to that
environment's database before the service starts, so a schema change ships as:
edit the schema, `npm run db:generate`, `npm run db:plan`, commit, push.

The deployed service does not read `DATABASE_URL` (on these projects it holds
the placeholder `-`). It receives the database it was wired to, and
`src/prisma/connection.ts` reads it from there.

Every other variable still comes from the environment. `next build` copies the
repository's `.env` into the server it produces, so a deploy currently runs
with the values committed in `.env`, including `NEXT_PUBLIC_SITE_URL` and the
storage keys. The alternative that keeps them out of git is the project's own
variables: `npx prisma project env add --file .env --role production` uploads
them once, and services receive them at their next deploy.

To run the same thing locally, with no Prisma account: `npm run prisma:dev`
starts a local Postgres, applies the migrations and serves the app;
`npm run prisma:dev:stop` ends it. Use the scripts rather than a bare
`prisma dev`: they run the app under the name `hyper-social-connection`,
because the trailing hyphen of the real project name makes every second
`prisma dev` start fail (the reason is in `module.ts`). To deploy from this machine instead of from
GitHub: `npx prisma auth login`, then `npm run prisma:deploy`.

### Prisma Compute (`prisma.compute.json`)

The older Compute deploy prepares the database itself by running
`prisma-next contract emit` and `prisma-next db init` against `DATABASE_URL`.
`prisma-next` is the pre-release name of the CLI that now ships as `prisma`, so
`tools/prisma-next-shim` (a local dev dependency) provides that command and
forwards it to the installed `prisma` CLI. On an empty database `db init`
creates the whole schema and records the contract marker; on a database that
already matches it does nothing.

### Vercel, Netlify, a plain Node server

These read `DATABASE_URL` from their own environment settings and only run
`npm run build`. They do not migrate anything: run `npm run db:migrate` against
the database once, before the first deploy and after every schema change.

## Querying

```ts
import { db } from '@/lib/prisma';
import { and, or, not } from '@prisma/orm-postgres/orm-client';

const user = await db.orm.public.User.where({ email }).first();        // row or null
const posts = await db.orm.public.Post
  .where((p) => p.userId.eq(id))
  .include('user', (u) => u.select('id', 'name'))
  .orderBy((p) => p.createdAt.desc())
  .limit(20)
  .all();
await db.orm.public.Post.where({ id }).update({ content });            // row or null
await db.orm.public.Like.where({ postId, userId }).deleteAndCount();   // number
```

Things that differ from Prisma 7:

- `update` and `delete` return `null` when no row matches; they do not throw.
- `deleteAndCount()` / `updateAndCount()` with no `where` affect every row.
- `upsert` can only target the primary key. For other unique columns the code
  updates first and then inserts with `createAndCount([...], { onConflict: 'skip', conflictOn: [...] })`.
- A failed statement throws `SqlQueryError`; the Postgres code is on
  `error.sqlState` (and `error.cause.code`), not `error.code`.
- Scripts must call `closeDb()` when done, or the pool keeps the process alive.

Raw SQL with `$1` placeholders goes through `rawQuery<T>(sql, ...values)`,
`rawExecute(sql, ...values)` and `rawTransaction(async (tx) => …)` in
`src/lib/prisma.ts`, which run on the same pool as the client.

## Auth tables

`User` maps onto the same `users` table the app has always used. `Session` /
`Account` / `VerificationToken` follow the standard Auth.js-compatible shape
for server-side sessions, OAuth linking, and email-verification tokens. The
app's current login (bcrypt + an opaque session cookie stored in `sessions`)
reads the same `users` table.
